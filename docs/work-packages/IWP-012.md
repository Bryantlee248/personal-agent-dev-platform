## 目标和威胁边界

验证**本机临时目录内静态虚构制品**的一次性事务：写前完整校验、程序自建 sandbox、切换、读回、提交；在受控子进程被强制终止后，新的前台调用能发现唯一事务并安全完成或回滚。它不是通用部署器，也不证明断电或磁盘控制器丢写后的自动恢复。

同一 Windows 用户账号内的恶意并发进程可以替换目录、伪造元数据或竞争句柄。Node 标准库无法在本约束内提供防止此类主动攻击的 OS 目录句柄沙箱；因此程序只在程序独占的、调用前为空的临时 base 中运行。一旦发现外部改写、路径重定向或状态不明，返回 `BLOCKED`，不执行删除。随机 token 和 marker 仅用于一致性校验，不作为权限证明。不得把此实验结果外推到生产部署或真实业务路径。

## 输入、路径与来源

- `start({ base, source, expectedSha, fault? })`：base 必须为调用前已存在、为空、非链接的系统临时目录直接或更深子目录；source 为现有静态目录；expectedSha 为完整小写 40 位 SHA。调用方不能指定 sandbox、release、current、target 或清理路径。
- `recover({ base, expectedSha })`：只通过原 base 发现事务，不要求进程死亡后不可能获得的异常对象、sandbox 路径或内存 token。base 中只能有预先规定的 intent、锁元数据和唯一 `txn-*` 子目录；出现第二个子目录或未知条目即 `BLOCKED`。
- start 在任何写入前规范化并检查 base/source、祖先 realpath、重叠、链接与目录为空；验证 source 后重新检查 base 身份。唯一 sandbox 用 `mkdtemp(base/txn-)` 创建。恢复时逐层检查 base、sandbox 和每个待处理条目，禁止 symlink/junction/reparse point；无法以 Node 标准库可靠识别的类型即 `BLOCKED`。清理只允许固定名称、固定深度和经检查的程序创建内容。
- base 从成功认领起为**一次性**容器；不在同一 base 启动第二个部署。事务结束后调用方在取证完成时删除整个独占 base。恢复不得删除 source 或调用前已有内容。

## 独占与崩溃后接管

- 认领前完成 source 和空 base 验证。候选 owner 在同一 base 写入**完整且已同步**的唯一临时记录，至少包含 PID、随机 run ID、base 身份、期望 SHA 和代际号；用 `fs.link` 将它原子发布为不可变的 `owner-000001`。记录发布后不得修改或删除已有 `owner-N`，临时记录只有新 owner 持有最高代际时才可按确定规则清理。Windows 目标卷上须先证明同名 hard link 只有一个竞争者成功，且 `EEXIST` 不覆盖原有记录。
- start 与 recover 均以**最高完整代际**为 owner。活 owner（`process.kill(pid, 0)` 成功或权限不明）一律 `LOCKED`，不靠心跳超时夺锁。只有确认最高代际 owner 不存在（`ESRCH`），候选者才能把完整且已同步的记录原子链接到**恰好下一代** `owner-(N+1)`；并发中仅链接成功者取得独占，失败者重新读取最高代际后保守返回 `LOCKED` 或有界重试。两个调用不得仅凭同一死代际同时开始清理。PID 重用只会保守阻断，不许可抢占。
- **发布前空窗**：若 base 仅有恰好一个完整、已同步、与 base/expectedSha 匹配的未发布 owner 候选，且没有 intent、sandbox 或任何 `owner-N`，其记录中的 PID 已确认不存在，恢复调用创建自己的完整 owner 记录并原子发布为 `owner-000001`；成功者写入 `FAILED` 回执并返回安全无操作结果，竞争失败者重新检查并返回 `LOCKED`。再次调用核实同一终态。若原候选 PID 仍活着则 `LOCKED`；候选损坏、多个候选或有其他条目则 `BLOCKED`。原候选留作证据，不得删除后假装 base 重新为空。
- 缺代际（上述唯一发布前空窗除外）、损坏或不匹配的 owner 记录、未知临时记录、链接原语不具备上述保证、无法判定进程已死或无法确认自己仍是最高代际，均返回 `BLOCKED` 并保留现场。任何恢复写入前后均核对自己仍为最高代际；已存在代际永久保留至调用方取证后清理整个一次性 base。此协议不使用 `rename(fixed, unique)` 或删除旧锁，避免误搬移新 owner。恢复过程再次崩溃时，下一次调用通过更高代际接管。

### 已提交事务的只读 orphan 例外

并发 `start` 的失败候选若在写入并同步后、链接代际前被强制终止，可能遗留一个与成功事务 run ID 不同的 `candidate-*`。它不得永久阻止**已提交且完整验证**的只读版本核对，但也不得成为恢复写入或清理许可。原“未知候选一律 BLOCKED”仍适用于所有非下述精确情形。

- 先在目标 Windows 临时卷验证 `fs.stat({ bigint: true })` 的 `dev`+`ino`：同一文件的 hard link 身份相等、独立文件身份不同，且身份值可用；验证不成立则 `BLOCKED`。对每个 candidate 先以 `lstat` 确认普通文件、非链接或 reparse point，再读取完整固定 schema、base、SHA、代际和 PID。正常 owner 对应的候选必须与恰好一个 `owner-N` 具有相同 `dev`+`ino` 和内容；名称、token 或 JSON 相等不能代替文件身份。
- 仅容许**最多一个**与任何 `owner-N` 均无相同文件身份的额外候选；其 schema 完整、base 和 expectedSha 匹配、代际为 `1`、run ID 与已提交事务不同，且 PID 经 `ESRCH` 证实死亡。最高 owner 的进程状态也必须可判定为已死亡。额外候选不得链接到任何代际、intent 或 sandbox；存在第二个额外候选、损坏记录、身份不明、活 PID 或额外目录时仍 `BLOCKED`。
- 仅当 intent、连续 owner 链、`COMMITTED` 日志、current、release 的 SHA、逐文件/整体摘要及 health 全部验证通过时，可保留这个额外候选并返回 `COMMITTED`。整个路径**只读**：不接管锁、不改日志、不删候选、不清理任何文件。不能用于 `NEW`、未提交或 `RECOVERING/FAILED` 的恢复；这些状态仍保守 `BLOCKED`。重复调用必须得到相同结果。

## 持久化与状态机

状态：`NEW → PREPARED → SWITCH_INTENT → SWITCHED → VERIFIED → COMMITTED`；未提交状态经 `RECOVERING → FAILED`。`COMMITTED` 与 `FAILED` 为幂等终态；`RECOVERING` 可重放。恢复不把 `VERIFIED` 直接当提交，未写入 COMMITTED 即回滚。

- intent 先记录 run ID、expectedSha、base 身份和协议版本，再创建 sandbox。崩溃于 sandbox 来源记录之前，只在 base 仍满足唯一事务且 sandbox 为空、名称符合程序生成格式时清理；否则 `BLOCKED`。
- 每次日志更新：写同目录临时文件、同步文件内容、原子替换正式文件；平台允许时同步父目录。日志包含版本、run ID、序号、前态、后态、expectedSha 和内容摘要。恢复只接受完整、单调、匹配 intent 的日志；损坏或撕裂的日志返回 `BLOCKED`，保留现场，不伪称回滚成功。
- `PREPARED` 前校验 source；复制至 staging 后再次校验全部文件。写入 `SWITCH_INTENT` 后才切换。current 只写固定的相对 release 标识，以同目录临时文件原子替换。`VERIFIED` 必须从 sandbox 读回 SHA、摘要和 health；`COMMITTED` 写入最终回执后才报告成功。
- `RECOVERING` 必须先落盘，再以可重复的固定路径操作清理未提交 release/current/staging；再次调用可重复清理并落 `FAILED`。`FAILED` 重复调用只读核实最终目录树并返回同一结果。
- Node/Windows 若无法证明目录项在断电后持久，本包仅验收强制进程终止后的恢复；不宣称断电恢复。任何同步或原子替换失败返回稳定错误码并保留现场供人工检查。

## Source 合同

只接受固定文件集合、规则文件、总大小上限和单文件上限；逐文件计算 SHA-256，再以规范顺序计算整体摘要。manifest 必须绑定完整 expectedSha、所有文件的名称/大小/摘要、整体摘要和 `health=PASS`。`health=FAIL`、额外文件、链接、摘要不一致、超限、重复/不规范名称均须在首次写入 base 前拒绝。source 内容只作为字节复制，绝不执行。复制后校验 staging 与首次读取的摘要完全一致，防止校验与复制间源文件变化。

## Delivery 后续包与验收矩阵

本包完成后，由 Architecture 另建 Delivery 主责工作包（拟 IWP-013），只授权现有 `ops/transactional-deploy`、`e2e/transactional-deploy.mjs`、对应 fixtures、证据目录和 `package.json`；不沿用 IWP-011 的两轮评审额度。因固定 SHA PR 契约只承认**可信 base**中 ACTIVE IWP 的 ownership，IWP-013 采用两步治理引导：先在 IWP-012 仍 ACTIVE 时，以仅修改其已拥有的 `PROJECT.json` 等路径的受保护 Architecture PR 登记 IWP-013 ACTIVE 及其 Architecture/Delivery ownership；正常五项检查合并后，再以可信 base 的 IWP-013 为依据，提交新增 IWP-013 文档的受保护 Architecture PR。第二步通过后才将 IWP-012 收尾。全程不移除第五项检查、不管理员绕过、不提前实施 Delivery。

Delivery 测试须断言**稳定 code、是否发生首次写入、精确最终目录树、source/base 原内容不变、二次 recover 幂等**，至少覆盖：

1. 正常 COMMITTED、从 sandbox 读回完整 SHA/摘要/health；指令文本仅字节复制。
2. 写前拒绝：base 非空/非临时/链接或 junction/与 source 重叠；source SHA、大小、逐文件与整体摘要、health、额外文件、链接、超限错误；base 保持空。
3. 故障点：`NEW`、`PREPARED`、`SWITCH_INTENT`、`SWITCHED`、`VERIFIED`、`RECOVERING`；每点以新的前台调用恢复，`FAILED` 可重复调用。
4. 真实终止：由受控的前台子进程在指定落盘点终止，父进程等待退出后恢复；覆盖唯一有效未发布候选（无 intent/sandbox → 安全 FAILED）、多个或损坏候选（→ BLOCKED）、已发布 owner 代际和日志临时文件。仅抛异常并执行 `finally` 的注入不算真实崩溃证据。
5. 并发与平台原语：同一 Windows 目标卷上两个候选 `fs.link` 到同名下一代仅一个成功且原记录不被覆盖；`dev`+`ino` 对 hard link 的同一性与独立文件的差异有可复现证明；活 owner 时第二调用为 `LOCKED` 且文件无变化；死 owner 的两个恢复者竞逐同一下一代，仅胜者能清理；胜者随即死亡时再由更高代际恢复。原语验证失败即 `BLOCKED`，不得改用 rename 接管。另测失败并发 `start` 在候选已同步、链接前终止：成功事务的已验证 `COMMITTED` 可在保留额外候选的条件下重复只读读回；候选活着、损坏、多个或文件身份不明时 `BLOCKED` 且目录逐字节不变。
6. 歧义：损坏日志、未知条目、额外 sandbox、链接替换、不能证明 owner 已死时均 `BLOCKED`，不执行清理；同步/替换失败保留现场。

验收次序：本地测试 → governance → converge → independent verify → build/test → 新文件 `git add -N` 后完整 diff 的最多两轮 Qwen 只读复核（plan mode、零普通工具调用、关闭聊天记录与遥测）→ 固定 head SHA 的 Delivery PR → 五项 required checks 全绿 → 正常受保护 squash 合并 → 独立 Architecture 收尾 PR。Architecture 与 Delivery 不自审自改；只有证据完整才将 W-007 标记 DONE，随后停止，不启动 W-008。
