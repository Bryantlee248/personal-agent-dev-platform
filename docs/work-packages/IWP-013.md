## 必须实现的契约

1. **写前验证**：base 的临时目录归属、非链接/非 junction、空目录、与 source 不重叠；source 固定文件集合、规范名称、上限、逐文件与整体 SHA-256、manifest 对完整 SHA 的绑定、`health=PASS`。全部完成之前 base 不产生任何写入。复制到 staging 后复核首次读取的全部摘要。
2. **唯一事务来源**：base 一次性使用；intent、不可变 owner 代际与唯一 `mkdtemp` sandbox 的身份互相绑定。恢复仅接受程序生成的固定结构；异常目录、链接或无法证明的来源返回 `BLOCKED`，不做清理。token/marker 只是校验数据，不作权限边界。
3. **并发锁**：按 IWP-012 的完整 fsynced owner 记录与单卷原子 `fs.link` 代际协议实施。必须先在目标 Windows 卷证明同名链接竞争只有一个胜者且旧记录不被覆盖。活 owner 或进程状态不明返回 `LOCKED`/`BLOCKED`；死 owner 仅竞争下一代，失败者不得清理。不能证明原语或身份时停止，不改用 rename 抢锁或超时锁。
4. **日志与恢复**：按 IWP-012 的持久化次序和 `NEW → PREPARED → SWITCH_INTENT → SWITCHED → VERIFIED → COMMITTED`、`RECOVERING → FAILED` 实施。日志写入、同步、原子替换及平台限制须可观察；`COMMITTED`/`FAILED` 幂等，`RECOVERING` 可重放。日志损坏、未知状态或磁盘同步失败时保留现场并返回稳定错误码，不声称成功回滚。
5. **真实中断发现**：由新的前台调用仅通过 base 发现进程死亡后的唯一事务。唯一完整但未发布的候选、无 intent/sandbox 且 owner 已死时，按 IWP-012 由新的活 owner 原子认领并生成安全 `FAILED`；多个或损坏候选、额外内容则 `BLOCKED`。
6. **已提交事务的只读候选例外**：严格按 IWP-012 合并后的“已提交事务的只读 orphan 例外”执行。先在目标 Windows 卷证明 bigint `dev`+`ino` 能区分 hard link 与独立文件；正常候选须与对应 `owner-N` 文件身份及内容一致。最多一个额外、未链接任何 owner、schema/base/SHA/代际完整、run ID 不同且 PID 已死亡的失败 `start` 候选，可在最高 owner 已死亡、intent/连续 owner 链/`COMMITTED` 日志/current/release 的 SHA、摘要与 health 全部核实后**保留原文件并只读返回 COMMITTED**。不得借此接管锁、清理候选或恢复未提交状态；活 PID、多个/损坏候选、文件身份不明或任一核验失败仍 `BLOCKED`，现场不变。
